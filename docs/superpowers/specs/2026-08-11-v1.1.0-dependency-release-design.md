# OpenRecall v1.1.0 Dependency and Release Design

## Objective

Publish OpenRecall `v1.1.0` from the current `main` functionality after a
source-level review of every open Dependabot pull request. Integrate every
compatible, useful update at the newest reviewed patch level, explicitly
reject incompatible updates, leave no stale bot pull request unexplained, and
publish a verified Windows ZIP plus SHA-256 checksum through GitHub Releases.

## Non-negotiable constraints

- The supported and bundled runtime remains Node.js `24.18.0`; the package
  engine remains `>=24.18.0 <25`.
- pnpm remains exactly `11.17.0` and all direct dependency versions remain
  exact.
- `@types/node` remains on the Node 24 line. Node 26 types must not be used to
  type-check a Node 24-only application.
- Production behavior, the SQLite schema, existing user databases, backups,
  and restore compatibility must not change merely because dependencies are
  refreshed.
- The Windows archive remains self-contained, supports normal and portable
  modes, opens the default browser, and never modifies NVDA or its settings.
- A native/build dependency version may change only after the repository's
  explicit allowlist, licenses, build, migrations, package contract, and
  extracted-package smoke tests all accept that exact version.
- A release is complete only when the public, non-draft GitHub Release points
  to tag `v1.1.0`, exposes both the ZIP and `.sha256`, and all required GitHub
  checks succeed on the release commit and tag workflow.

## Pull-request disposition

The Dependabot branches overlap, contain slightly stale targets, and one group
mixes compatible tooling with incompatible Node 26 types. Merging them one by
one would knowingly land stale or internally inconsistent baselines. The
release branch therefore integrates the reviewed versions in one controlled
dependency commit. Once that commit is on `main`, each bot PR receives a
specific comment and is closed as superseded:

| PR | Disposition |
| --- | --- |
| `#7` `@fastify/sse 0.6.0` | Superseded by the same accepted version. |
| `#9` `fastify 5.11.2` | Superseded by reviewed `5.11.3`; the prior Windows optimizer failure is reproduced or cleared against the combined deterministic baseline before closure. |
| `#10` `tsx 4.23.11` | Superseded by `4.23.12` plus explicit `esbuild 0.28.2` native-policy approval. |
| `#11` `typebox 1.3.11` | Superseded by reviewed `1.3.12`. |
| `#12` `vite 8.2.1` | Superseded by the same accepted version. |
| `#13` `better-sqlite3 13.0.3` | Superseded by the same accepted version plus explicit native-policy and Windows database verification. |
| `#15` grouped development tooling | Compatible members are superseded; `@types/node 26.2.0` is explicitly rejected because OpenRecall targets Node 24. |

Dependabot configuration will ignore semver-major `@types/node` updates while
the project targets Node 24. Patch/minor updates within Node 24 remain eligible.
The comments must link to the release/dependency commit and state the exact
replacement or incompatibility; generic "closing" comments are insufficient.

## Fastify Windows failure investigation

PR `#9` previously failed one Windows accessibility/E2E run because the
official step optimizer produced `127` seconds where the fixture expected the
historical `186` seconds; the same run also timed out before applying a profile.
This is not accepted as either a Fastify regression or a harmless flake without
evidence.

The release branch must:

1. run the optimizer durability test repeatedly before dependency changes to
   establish whether the current test is platform/time sensitive;
2. run it repeatedly after the Fastify update with the exact Node 24 runtime;
3. inspect seeded review times, worker determinism, and assertion semantics if
   either baseline is unstable;
4. fix the root cause or make the fixture deterministic without weakening the
   requirement that official output is applied and restored;
5. retain assertions for no silent due-date rewrite, stale-result rejection,
   cancellation, parameter application, rollback, and SQLite durability.

Increasing timeouts or accepting either arbitrary recommendation is not a valid
fix unless the official upstream algorithm contract proves that the numeric
value is intentionally non-deterministic and the test still proves the saved
minute conversion correctly.

## Release identity and single source of truth

Every workspace manifest moves from `1.0.1` to `1.1.0`. The root
`package.json` becomes the canonical release identity:

- `package:windows` calls the packager without a duplicated literal version;
- `scripts/package-windows.mjs` reads the root version when `--version` is
  omitted while retaining the explicit option for tests and diagnostics;
- `.github/workflows/release.yml` resolves `VERSION`, `ARCHIVE_NAME`, release
  title, artifact name, and `docs/releases/v${VERSION}.md` from the checked-out
  root manifest;
- a tag build must fail before packaging if `github.ref_name !== v${VERSION}`;
- package-contract tests prove the default and explicit version paths, archive
  name, embedded `VERSION.txt`, and tag/archive identity checks.

This removes the previous four-way manual duplication that left `main` twenty-
four commits ahead of the public `v1.0.1` download.

## Release documentation

`CHANGELOG.md` moves the current `Unreleased` entries into a dated `1.1.0`
section and adds the optimizer work that is already on `main`:

- layered global/per-section optimizer training controls and compatibility
  boundaries;
- official learning/relearning-step analysis with exclusions/statistics;
- apply, stale protection, and restore without rewriting stored due dates;
- exact duration presentation, isolated live announcement, and async scope-race
  protection;
- import-note previews, lazy collapsed section content, immediate review
  completion, and due-card priority;
- reviewed dependency refresh and continued Node 24 support.

`docs/releases/v1.1.0.md` provides user-facing highlights, Windows install and
portable launch guidance, automatic SQLite migration/backup advice, accessibility
notes, dependency/runtime statement, SHA/provenance verification, and known
limitations. English and Arabic README download instructions identify
`OpenRecall-v1.1.0-windows-x64.zip` and link to the latest release page.

## Verification ladder

Dependency and release changes advance only through these gates:

1. exact dependency installation and supply-chain policy;
2. adapter boundaries, committed whitespace, type checks, licenses, and unit /
   property / integration tests;
3. database migration, backup, restore, rollback, and native module tests;
4. production build and loopback server smoke;
5. complete Playwright/axe matrix in Arabic, English, pseudo-locale, PWA, and
   optimizer projects at normal and 320-pixel reflow widths;
6. Windows package contracts;
7. fresh Windows ZIP construction and SHA-256 generation;
8. extracted archive smoke in normal and portable modes;
9. independent read-only code/release review with no unresolved Important or
   Critical finding;
10. protected release PR checks: Release gates, Playwright and axe, Windows
    stable Chrome, CodeQL, and dependency review;
11. post-merge `main` checks, then tag workflow success;
12. public Release audit: non-draft/latest tag `v1.1.0`, exact target commit,
    ZIP and SHA assets, checksum match after downloading, provenance/attestation
    presence where GitHub exposes it, and zero open dependency/code/secret
    scanning alerts.

## Integration and rollback

All source changes land through `release/v1.1.0` and one protected pull request
to `main`, using squash merge to preserve the repository's linear-history rule.
No tag is created before the merged `main` commit is green. The release workflow
attests the ZIP through GitHub artifact attestations, creates the release as a
draft, uploads both assets, then publishes it only after successful upload.

If a dependency cannot pass the full ladder, it is removed from the release
commit and its bot PR is left open with the concrete blocker, unless it is
incompatible by policy (such as Node 26 types), in which case it is closed with
that reason. If tag publishing fails before a public release exists, fix the
source/workflow on `main`, delete only the failed unpublished tag after verifying
there is no public release, then retry with explicit audit evidence. Published
tags and assets are never silently replaced.

## Completion criteria

The work is complete only when all of the following are simultaneously true:

- every bot PR existing at the start has an evidence-backed merged/superseded or
  incompatible disposition;
- `main` contains the reviewed dependency baseline and version `1.1.0`;
- tag `v1.1.0` resolves to the verified release commit;
- all source, PR, `main`, Windows, security, and release workflows are green;
- the public latest release contains a downloadable Windows ZIP and checksum;
- a fresh download hashes to the published checksum and launches in both modes;
- GitHub reports no open Dependabot, code-scanning, or secret-scanning alert;
- repository and release notes accurately describe what users receive.
